# Session Activity Status Specification

## Problem Statement

A session row reports whether its **shell** is alive, not what its **agent** is doing:
`SessionStatus` is `'running' | 'stopped'`, derived from membership in the running Map
(`session-manager.ts:290`, `config.ts:10`), and the rail row renders the literal
`running`/`stopped` beside a status dot (`SessionRail.tsx:284-285`). With several agents
running in parallel, the only way to learn whether one has finished, is blocked on a
permission prompt, or hit a rate limit is to attach to it and read the terminal. The rail's
"N running" counter has the same blind spot — it counts live shells, not working agents.

Claude Code publishes a documented lifecycle-hook API (`code.claude.com/docs/en/hooks`) that
reports exactly these transitions — prompt submitted, tool started and finished, permission
requested, turn finished, turn failed, compaction, session ended. This feature consumes it.

## Goals

- [ ] A running Claude session shows what its agent is doing: working, waiting for a prompt, blocked on an approval or an input, failed, compacting, or exited back to the shell
- [ ] The state comes from a documented Claude Code interface, not from reading the terminal screen, so it survives Claude Code's frequent releases
- [ ] A long task that prints nothing still reads as working
- [ ] The rail header reports how many agents are working and how many need the user
- [ ] Sessions the app cannot judge keep today's behaviour instead of guessing

## Out of Scope

| Feature | Reason |
| ------- | ------ |
| Activity state for ad-hoc sessions | Owner decision: only registry agents get the state. The app does not know which CLI a raw command runs |
| Activity state for registry agents other than Claude Code (Codex, opencode, Copilot) | Each CLI has its own mechanism, none of them verified in this feature. Their rows keep today's `running`/`stopped` |
| Reading the terminal screen or the PTY stream to infer state | Rejected at Design with measurements: ConPTY forwards a cell diff, and every on-screen marker is undocumented UI that changes between Claude Code releases (`design.md` §Rejected Approaches) |
| Letting the hook answer on the agent's behalf (allow/deny a permission, block a stop) | The app observes; it never decides. See ACTV-10 |
| Persisting activity across restarts | The PTY never survives a restart; every session loads as `stopped` (`session-manager.ts:61-66`) |
| A per-session history or timeline of tool calls | The row and the detail pane show the current state only |
| Taskbar badge or overlay icon | Owner chose the rail and the detail pane |
| Notifying the user on a state change | Feature `session-idle-notifications`, which builds on this one |
| Editing the injected hook configuration | The configuration is an implementation detail of the app, generated per launch |
| Consuming the `quota_auto_resume_*` notifications (owner deferred, 2026-09-15) | A session paused by a claude.ai usage limit reports `error` from `StopFailure` `rate_limit` and **stays there** after Claude resumes on its own, because Claude Code sends no `idle_prompt` while it waits for the reset. Closing it is three Transition Table rows — `_fired` → `working`, `_stale` → `needs-input` (it waits for Enter), `_disabled` → `waiting` — and needs Claude Code v2.1.234+. Follow-up, not a defect in what ships here |

## Assumptions & Open Questions

| Assumption / decision | Chosen default | Rationale | Confirmed? |
| --------------------- | -------------- | --------- | ---------- |
| Source of the state | Claude Code **lifecycle hooks**, delivered to the app over loopback HTTP | Documented, versioned API; the owner rejected screen scraping because Claude Code updates constantly and every screen marker is undocumented | y |
| Hook type | `type: "http"`: Claude Code POSTs the event JSON to a URL | No process spawned per event. Documented outcomes: 2xx empty body = success with no decision; non-2xx and connection failure = non-blocking error, execution continues (`hooks.md` §HTTP response handling) | y |
| How the hooks reach one session | `claude --settings <file>` appended to the launch command, generated by the app | `--settings` accepts a file path or JSON, applies for one session only and writes no file; hook entries **merge** with the user's own hooks (`settings.md` §Change a setting for one session, `hooks.md` §Hook locations). Verified at Design with zero-token launches: the injected `SessionStart`/`SessionEnd` fired | y |
| Which sessions get hooks | Registry agents whose command normalizes (`commandKey`) to `claude` | Same identity rule as `undoByteFor`: survives a rename, a full path and a `.exe` suffix | y |
| Session identity on each request | A per-session random token in an environment variable the app sets on the PTY, sent as `Authorization: Bearer $VAR` via the hook's `allowedEnvVars` | Hooks inherit the parent environment (`hooks.md`, verified at Design). The token is both authentication and routing, the pattern of the workflows `emit_result` server (AD-008) | y |
| Where `commandKey` lives | Moved from `renderer/src/lib/terminal-keys.ts` to `src/shared/` and imported by both | Injection is decided in main; main must not import renderer code | y |
| After a permission is approved | No hook fires until the approved tool finishes, so the **user's next keystroke** to a session that is `needs approval` or `needs input` moves it to `working` | Documented gap: `PermissionRequest` fires before the dialog, and the next event is `PostToolUse` when the tool ends. Without this rule an approved 10-minute build reads `needs approval` for 10 minutes. Answering the dialog *is* a keystroke, and the app already sees every keystroke (`SessionManager.input`) | y |
| What counts as a keystroke | Any `session:input` data that is not a terminal mouse report or focus report | Claude Code enables mouse reporting (`ESC[?1003h`), so hovering over the terminal sends input bytes. Those must not answer a dialog the user never touched | y |
| User interrupt (Esc) | No hook fires on interrupt (`hooks.md` §Stop: "Does not run if the stoppage occurred due to a user interrupt"). The session keeps its last state until the next event; `idle_prompt` (~60 s idle) moves it to `waiting` | Documented limitation, accepted. The residual error is a stale `working`, the cheap direction | y |
| Failure posture | Never derive `waiting` or `needs approval` without an event that says so. No event yet, or hooks disabled, = no activity state (today's `running`) | A false "your turn" is the expensive error; an absent state costs nothing that exists today | y |
| Activity lifetime | Ephemeral: derived in main, never written to `config.json` | The PTY does not survive a restart, so a persisted activity state could only ever be stale | y |
| How the renderer receives it | A `session:activity` event carrying the new activity, applied in place | `use-sessions.ts:43` refetches the whole list on `session:status`; at tool-call frequency that is a round-trip per tool | y |
| Tool name on the row | The row label stays `working`; the running tool's name shows in the tooltip and the detail pane | Owner decision: Claude chains several tools per second and a label that changes per call is unreadable | y |
| Token cost | None. Hooks are local POSTs; tests use documentation-shaped payloads; no recording is needed | Owner concern at Design, answered by the hook approach | y |
| **[amended 2026-09-15, after the owner-run smoke]** `SessionStart` over http | **Not delivered.** Claude Code 2.1.273 fires `SessionStart` to a `command` hook and not to an `http` one, at launch **and** mid-session after `/clear`. A freshly spawned session therefore holds no activity and renders `running` until its first turn, and `SessionEnd` `clear`/`resume` means `waiting` because nothing else would correct it | Measured three ways with zero-token probes: both hook types on the same event in one session (command fired, http did not); a `/clear` mid-session (only `SessionEnd reason=clear` arrived); and a fresh session idle for 100 s (no `idle_prompt`, which the docs gate on Claude having responded). Owner chose to accept it rather than add a shell-dependent `command` hook | y |
| Foreground-child-process detection | Not used | node-pty exposes no foreground process on Windows, and the agent is one process in both states (`design.md` §Rejected Approaches) | y |
| Auth boundaries, rate limits, external-dependency failure | The hook endpoint listens on `127.0.0.1` only and requires a live session token; Claude Code treats an unreachable endpoint as a non-blocking error | The only external party is the local Claude Code process the app itself launched | y |
| Observability | A rejected or malformed hook request is logged once per session in main | The symptom of a broken hook path is a session stuck without state, which the log explains | y |

**Open questions:** none - all resolved or logged above.

## Transition Table

Normative for ACTV-03. `tool` and `subagents` are details carried alongside the state (P3).

| Hook event (payload discriminator) | New state | Detail effect |
| ---------------------------------- | --------- | ------------- |
| `SessionStart` (`source` = `startup`, `resume`, `clear`, `fork`) *(not currently delivered over http — AD-020; the mapping is kept for the day it is)* | `waiting` | clear tool, subagents = 0 |
| `SessionStart` (`source` = `compact`) *(same)* | unchanged | — |
| `UserPromptSubmit` | `working` | clear tool |
| `PreToolUse` | `working` | tool = `tool_name` |
| `PostToolUse`, `PostToolUseFailure` | `working` | clear tool |
| `PermissionRequest` | `needs approval` | tool = `tool_name` |
| `Notification` (`notification_type` = `permission_prompt`) | `needs approval` | — |
| `Elicitation`; `Notification` (`elicitation_dialog`, `elicitation_url_dialog`) | `needs input` | — |
| `ElicitationResult` | `working` | — |
| user keystroke while `needs approval` or `needs input` | `working` | — |
| `Stop` | `waiting` | clear tool |
| `Notification` (`idle_prompt`) | `waiting` | clear tool |
| `StopFailure` | `error` | error = `error` field |
| `PreCompact` | `compacting` | remember the prior state |
| `PostCompact` | the state held before `PreCompact` | — |
| `SubagentStart` / `SubagentStop` | unchanged | add / remove `agent_id` from the active set |
| `SessionEnd` (`reason` ≠ `clear`, `resume`) | `exited` | clear tool, subagents = 0 |
| `SessionEnd` (`reason` = `clear`, `resume`) | `waiting` | clear tool, subagents = 0 (the CLI stays up at a fresh prompt) |
| any other event or notification type | unchanged | — |

## User Stories

### P1: The session knows what its agent is doing ⭐ MVP

**User Story**: As a user running several agents at once, I want each session to know
whether its agent is working, waiting for me, blocked on an approval, failed, or gone, so
that I can tell which one needs me without attaching to it.

**Why P1**: The vertical slice — hook injection, the loopback endpoint, the state machine in
main, the event across IPC, a visible label on the row. Everything else refines it.

**Acceptance Criteria** (each line is one EARS pattern):

1. WHERE a session's registry agent command normalizes to `claude` the app SHALL launch it with a hook configuration that reports that session's lifecycle events to the app, without writing to any Claude Code settings file.  <!-- optional-feature -->
2. WHERE a session is ad-hoc, or its agent command does not normalize to `claude`, the app SHALL inject no hook configuration, derive no activity state, and render the row exactly as it does today.  <!-- optional-feature -->
3. WHEN the app receives a hook event carrying a live session's token THEN it SHALL apply the event to that session as the Transition Table specifies.  <!-- event-driven -->
4. IF a hook request carries no token, a token of no live session, or a body that is not a JSON object THEN the app SHALL change no session's state.  <!-- unwanted-behavior -->
5. WHEN a session's activity changes THEN the app SHALL emit `session:activity` carrying the session id and the new activity.  <!-- event-driven -->
6. IF applying an event yields the activity the session already holds THEN the app SHALL NOT emit an event.  <!-- unwanted-behavior -->
7. WHEN the renderer receives `session:activity` THEN it SHALL update that session in place without re-fetching the session list.  <!-- event-driven -->
8. WHEN a session stops THEN the app SHALL discard its activity, revoke its token, and render `stopped`.  <!-- event-driven -->
9. The app SHALL NOT write any activity state to `config.json`.  <!-- ubiquitous -->
10. The app SHALL answer every authenticated hook request with a 2xx status and an empty body, so that a hook never allows, denies, blocks or continues anything on the agent's behalf.  <!-- ubiquitous -->
11. The injected hook configuration SHALL bound each hook with a timeout of at most 5 seconds, so that an unresponsive app cannot stall the agent.  <!-- ubiquitous -->
12. WHILE a session is `needs approval` or `needs input`, WHEN the user sends a keystroke to that session THEN the app SHALL set it to `working`.  <!-- complex -->
13. WHEN a session starts or respawns THEN the app SHALL issue it a fresh token and hold no activity state until its first hook event arrives.  <!-- event-driven -->

**Independent Test**: Start a Claude session — the row reads `running` until the first
prompt, because `SessionStart` never arrives. Ask for a shell command that needs approval: `working`, then `needs approval` the moment
the dialog opens; approve it and the row reads `working` for the whole silent run, then
`waiting`. Type `/exit`: `shell`. Start an ad-hoc `pwsh` session: `running`, exactly as
before.

### P2: The state is legible on the row and in the rail header

**User Story**: As a user scanning the rail, I want each state to read at a glance —
icon plus word — and the header to tell me how many agents are working and how many need me.

**Why P2**: The state is already correct and visible as text after P1; this is how it is
presented. Separable, demoable on its own.

**Acceptance Criteria**:

1. WHILE a session is `working` or `compacting` its row SHALL show an animated loader beside the label `working` or `compacting`.  <!-- state-driven -->
2. WHILE a session is `waiting` its row SHALL show a steady indicator beside the label `waiting`.  <!-- state-driven -->
3. WHILE a session is `needs approval` or `needs input` its row SHALL show an attention indicator, distinct in colour from `waiting`, beside the label `approval` or `input`.  <!-- state-driven -->
4. WHILE a session is `error` its row SHALL show an error indicator beside the label `error`.  <!-- state-driven -->
5. WHILE a session is `exited` its row SHALL show the handoff's `shell` status (label `shell`, `--amber`).  <!-- state-driven -->
6. WHILE a session is stopped, or running with no activity state, its row SHALL render exactly as it does today.  <!-- state-driven -->
7. WHERE the operating system requests reduced motion the loader SHALL NOT animate.  <!-- optional-feature -->
8. The row's status element SHALL expose an `aria-label` naming the state it displays.  <!-- ubiquitous -->
9. WHEN one or more sessions are `working` or `compacting` THEN the rail header SHALL report their count as working.  <!-- event-driven -->
10. WHEN one or more sessions are `needs approval`, `needs input` or `error` THEN the rail header SHALL report their count as needing the user.  <!-- event-driven -->

**Independent Test**: With one agent working, one waiting and one on an approval prompt, the
three rows are distinguishable without reading the text, the header reads one working and
one needing you, and a screen reader announces each row's state. With reduced motion enabled
the loader is static.

---

### P3: Detail — which tool, how many subagents, which error

**User Story**: As a user, I want to see which tool a working agent is running, whether it
has subagents out, and why a turn failed, without attaching to the terminal.

**Why P3**: The row already says *what state*; this says *what exactly*. Owner decision:
the detail lives in the tooltip and the detail pane, never in the row label.

**Acceptance Criteria**:

1. WHILE a session is `working` with a tool running, its row tooltip and its detail-pane status SHALL name that tool.  <!-- state-driven -->
2. WHILE a session has one or more active subagents, its row tooltip and its detail-pane status SHALL show the count.  <!-- state-driven -->
3. WHILE a session is `error`, its row tooltip and its detail-pane status SHALL show the error type from the `StopFailure` event.  <!-- state-driven -->
4. WHILE a session has an activity state, the detail-pane status pill SHALL show that state in place of `running`.  <!-- state-driven -->

**Independent Test**: While Claude runs a Bash command, hovering the row shows `Bash`; with
an Explore subagent out it shows `1 subagent`; after a forced rate limit it shows
`rate_limit`. The detail pane's pill mirrors the row.

## Edge Cases

- IF the user interrupts a turn (Esc) THEN the app SHALL keep the session's last state until the next hook event, and an `idle_prompt` notification SHALL move it to `waiting`.  <!-- unwanted-behavior -->
- IF hooks never report for a session (disabled by `disableAllHooks`, an org `allowManagedHooksOnly` policy, or `--bare` in the agent's args) THEN the session SHALL hold no activity state and its row SHALL render `running` as today.  <!-- unwanted-behavior -->
- IF a session's registry agent is edited or deleted while that session runs THEN the app SHALL keep the injection and token decided when the session started.  <!-- unwanted-behavior -->
- WHEN a session is stopped while any activity state is held THEN `stopped` SHALL win and no activity SHALL survive.  <!-- event-driven -->
- IF a hook request for a session arrives after that session stopped THEN the app SHALL ignore it.  <!-- unwanted-behavior -->
- IF `session:input` data is a mouse report or a focus report THEN it SHALL NOT count as a keystroke.  <!-- unwanted-behavior -->
- IF a `PostToolUse` arrives with no tool recorded, or a `SubagentStop` names an agent not in the active set, THEN the app SHALL apply the event without error and the subagent count SHALL never go below zero.  <!-- unwanted-behavior -->
- IF the agent process dies without a `SessionEnd` while its shell lives THEN the session SHALL keep its last state until the PTY stops or a respawn.  <!-- unwanted-behavior -->

## Success Criteria

- [ ] A minute-long agent task that prints nothing for stretches never reads `waiting`
- [ ] An agent that finishes its turn reads `waiting` within one second of the `Stop` hook
- [ ] A permission dialog reads `needs approval` within one second of opening, and an approved long tool reads `working` from the keystroke that approved it
- [ ] An ad-hoc session's row is byte-identical to its pre-feature rendering
- [ ] No test and no fixture requires running Claude Code or spending tokens
